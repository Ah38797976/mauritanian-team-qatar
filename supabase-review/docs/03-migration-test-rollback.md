# 03 — الترحيل والاختبار والاسترجاع

## النسخة الآمنة (موجودة الآن)
- `backup/mauritanian-team-prototype-task06-readiness.zip` داخل الأرشيف = نسخة Task 06 الأصلية بلا أي تعديل، بصمتها `dfb6298e…dfcdf` (SHA-256).
- مجلد `mauritanian-team-prototype/` مطابق بايتًا لها (يُثبته `MANIFEST.sha256`).
> ملاحظة (نسخة المستودع): `MANIFEST.sha256` و`backup/` غير مضمَّنين في هذا المستودع عمدًا (محفوظان في الحزمة الأصلية). انظر قسم «مراجع تاريخية» في `README.md` بالجذر.
- قبل أي عمل لاحق: وسم (tag) في Git للحالة الحالية، ونسخة ZIP محفوظة خارج الجهاز.

## البيئات
1. **الآن:** لا شيء متصل. الحزمة نصوص مراجعة.
2. **Staging:** مشروع Supabase **منفصل** للتجارب، بيانات وهمية فقط، يُنشئه المالك أو بموافقته الصريحة.
3. **Production:** مشروع آخر لاحقًا، ولا يُنشأ ولا تُدخل فيه بيانات حقيقية إلا ببوابة موافقة مستقلة.

## ترحيل البيانات الوهمية (staging فقط)
1. إنشاء 7 مستخدمين تجريبيين في Auth (بريد `…@example.invalid` أو نطاق اختبار يملكه المالك).
2. تشغيل `0006` (المرجع) ثم `0007` (يتطلب علم أمان `app.allow_fake_seed='yes'` ويرفض العمل بدونه).
3. معرّفات `p1…p12`, `m1…m3` من النموذج تُحوَّل إلى UUID ثابتة (انظر `0007`) لتبقى الاختبارات قابلة للمقارنة.
4. التحقق: عدّ الصفوف (12 لاعبًا، 4 طاقم، 3 مباريات، 6 أحداث، 19 مشاركة في المباريات، 24 سجل حضور) ومطابقة الإحصاءات المعروضة مع النموذج.
5. لا تُنقل بيانات الذاكرة الحية؛ المصدر هو `data.js` فقط.

## الاختبار
| المستوى | ماذا | كيف |
|---|---|---|
| قاعدة البيانات | مصفوفة الأدوار على الجداول والـRPC، وكتابة مباشرة مغلقة، وسجل التدقيق غير قابل للتعديل | `sql/tests/rls_matrix.sql` (pgTAP، داخل معاملة تُلغى) |
| سلب (Negative) | إرسال `team_id`/دور مزوّر، استدعاء RPC بمعرّف فريق آخر، قراءة صور فريق آخر، كتابة مباشرة بالمفتاح العام، نمط مفتاح سري داخل الملفات | حالات إضافية تُكتب مع أول تشغيل |
| الواجهة | اختبارات Task 06 الأربعة الحالية (337 فحصًا) بلا تعديل على النموذج الأصلي؛ ثم نسخة متصلة خلف علم تشغيل في فرع منفصل | Playwright |
| أمان | مراجعة مستقلة لدوال `SECURITY DEFINER`، وفحص المفاتيح، وCSP | قبل أي بيانات حقيقية |

معيار القبول لبوابة staging: كل اختبارات قاعدة البيانات تنجح، ولا فحص سلب ينجح بتجاوز، والواجهة المتصلة تُنتج نفس النتائج المرئية لكل دور كما في النموذج.

## الاسترجاع (Rollback)
| الحالة | الإجراء |
|---|---|
| خطأ في ترحيل (staging) | تشغيل `sql/down/000N_down.sql` بالعكس (7 → 1) أو إعادة إنشاء المشروع (الأسرع في staging) |
| قبل أي ترحيل | `pg_dump` كامل + نقطة استرجاع (PITR/النسخ الاحتياطية — يُتحقق من توفرها في خطة الحساب قبل الاعتماد عليها) |
| خطأ في الواجهة | العودة إلى وسم Git / ZIP الخاص بـ Task 06؛ النموذج الأصلي لا يعتمد على الخادم أصلًا |
| الإنتاج لاحقًا | نافذة صيانة، نسخة قبل كل خطوة، وخطة إيقاف الدخول (تعطيل Auth مؤقتًا) |
تنبيه: `0001_down` **يحذف كل بيانات الفريق**؛ للاستخدام في staging فقط.
